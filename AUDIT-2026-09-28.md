# OSAConnect pre-pilot audit — 2026-09-28

**Verdict: NOT READY for the pilot.** 9 critical issues. The worst: anyone on the internet can get the live
database password from an error page, make themselves an admin without logging in, read every student's
password, and change any student's service hours.

> **Keep this file private.** It describes how to attack the live system. Don't share it outside the team or
> commit it to a public repository until the critical issues are fixed.

## How it was tested

- No code was changed during the audit. Test scripts ran only from a scratch folder.
- **Live site** (`https://osaconnect.vercel.app`, commit `18229f1`): read-only requests, plus two logins using
  the hardcoded usernames and passwords. No live data was created, edited or deleted.
- **Everything that writes data** ran on throwaway local MongoDB databases, deleted afterwards. Email went to
  Django's in-memory test mailbox; no real email was sent.
- Code audited: branch `transition` plus 14 uncommitted local files.
- Labels: **CONFIRMED live** (seen on the live site), **CONFIRMED test** (seen on a test database),
  **FROM CODE** (read in the source, not run).

## Status of the known issues from the 2026-09-23 notes

- **Still present:**
  - Everything is `AllowAny`, and page access checks only the browser's saved role (localStorage)
  - Plaintext passwords, and the student ID as the default password
  - Hardcoded logins in `api/index.js`
  - `/health/` seeds default accounts and students into an empty database (CONFIRMED test)
  - Password reset has no attempt limit
  - DEBUG, ALLOWED_HOSTS and CORS settings (DEBUG is True in production, CONFIRMED)
  - "Completed today" is always 0, and notifications show "A student"
  - The guard's incident date is ignored
  - The app's violation names don't match; bulk reports always get 4 h
  - Offense counts include dismissed reports
  - Duplicate-name, name-linking and placeholder rules
  - Guard History shows every guard's reports
  - Faculty has no page
- **Changed:**
  - The MongoDB string is gone from current files but remains in git history, and is now publicly exposed through C1.
  - Student dashboards now ask only for their own records, but the API still gives everything to anyone.
  - There's no manual code entry on the website, but the old codes are still in the built files.
  - The offline gap is closed on Android (30 s locally, 3 min on live). The website still can't track in the background.
  - Timezones are fixed locally (UTC), not deployed yet, and the database has mixed records.
  - "Cleared" is never used; "Finished" appears only in filters.
  - `Procfile` and `build.sh` were removed, and Expo is SDK 57, not 54.
- **Fixed:**
  - The app no longer uses the phone's own position as the geofence center.
  - Selfies were removed from time-log downloads.
  - Hours can't go negative through time-out, and a second time-out doesn't deduct again.
  - The website and the app use the same countdown formula.
  - Registration codes are limited to 5 tries.

## Must fix before the pilot (in order)

1. Set `DEBUG=False` on Vercel, fix H1, then **rotate the Atlas password** and update it on Vercel and in `backend/.env`. (C1, H1)
2. Delete the hardcoded logins in `api/index.js` and the `/health/` seeding. (C4)
3. Stop sending `password` in any API response, hash passwords, and don't let placeholder students log in. (C3, C9)
4. Add real login tokens with role checks on every endpoint: students see only their own records, guards and staff can file reports, admins can do the rest. Replace `X-OSA-User`, and lock down `POST /users/` and all DELETE and PUT routes. (C2, C5, H4)
5. Remove or admin-lock `custom`, `set_start` and `manual_time_in/out`, and validate hours on approve and bulk reports. (C6)
6. Add attempt limits to password reset and login. (C8)
7. Make approval atomic. (H2)
8. Fix how guard reports match students: by ID only, no placeholder takeover. (H3)
9. Deploy the pending fixes, clean up the 8-hour records, and build and distribute APK 1.1.0 in the same release. (H5, H6)
10. Decide on the website's background gap, and word the thesis claim accordingly. (H7, C7)

## What could not be tested

- **Real camera scanning, real GPS, walking out of the area:** no phone available.
- **Android background tracking and notifications:** the APK with them isn't built, and Expo Go can't run them.
- **The website in a browser:** no browser automation was run, so these weren't checked: layout at 360/768/1280 px, dark and light modes, 404 pages, crashes on an empty database, permission-denied messages, console errors, and slow or offline connections.
- **Writes on the live site and real email delivery:** not allowed by the audit rules.
- **Concurrency over a real network:** tested only with threads inside one process.
- **Load:** estimated, not measured. With 20 students, 2 admins, 5-second polling and location pings, that's roughly 670 requests per minute and about 3–4 MB per minute, mostly from admin tabs.
- **Thesis claims:** there's no "Ready for Clearance" status in the code, notifications are email plus Android local notifications (not real-time push), "Cheating" (an academic violation) is in the punishment table, and "tamper-proof" doesn't hold because of C6 and C7.
